# WSB 稳定性与防滥用清理方案

## Problem Statement

WSB 将作为公开 WhatsApp 机器人运行，任何人都可以使用主要功能。当前实现缺少统一的用户限流、全局并发、请求队列和费用预算控制；同时存在 cron 重复注册、断线只重试一次、JSON 状态可能损坏后被清空、提醒重启丢失等可靠性问题。

目标是在不引入数据库或外部基础设施的前提下，让公开访问不会被单个用户或突发流量拖垮，也不会让 OpenRouter 费用失控；当资源接近上限时自动降级，而天气、帮助等非 AI 功能继续可用。

## Context

- WSB 是单进程 Node.js CommonJS 应用，由 PM2 管理，通过 `whatsapp-web.js` 接收消息。
- AI 请求由 `ai.js` 直接调用 OpenRouter，并按模型列表串行 fallback；所有调用共享部署密钥。
- 当前仅按用户序列化智能回复，没有全局并发上限、有限队列、每日预算或统一限流。
- `ready` 事件每次都会重新注册新闻、健身和汇率 cron；重新连接可能造成重复发送。
- `disconnected` 只安排一次重新初始化；失败后进程可能保持 online 但不再服务。
- memory、cache、autoreply 和 session 使用本地 JSON；部分模块直接覆盖文件并把读取失败当成空状态。
- `!remind` 只使用进程内 timer，PM2 重启后丢失。
- 2026-07-17 已通过 commit `b879231` 修复网站索引 stored XSS 和跨用户 reply-cache 泄漏，并增加安全回归测试。

## Chosen Approach

采用 **集中式本地防护层**：在现有单机 PM2 架构内新增统一 policy、限流、预算账本和 AI executor；使用原子写入的小型本地状态文件跨重启保存每日用量；同时整理连接、cron、提醒和 JSON 持久化生命周期。

公开机器人采用分级权限：低风险功能公开；所有 AI/高资源功能受额度保护；`!groups`、广播、建站和网站删除等敏感功能仍只允许 owner 或明确白名单。

默认 OpenRouter 每日硬预算为 **US$3**。接近预算或负载上限时优先自动降级到便宜模型和较短输出；达到硬上限后停止当天新 AI 请求，但非 AI 功能继续运行。

## Why This Approach

### 选择理由

- 与现有单进程架构一致，不需要 Redis、数据库迁移或额外守护服务。
- 所有 AI 入口经过同一 executor，避免命令各自实现限流后出现绕过路径。
- 预算预留与结算可防止多个并发请求同时突破硬上限。
- 本地原子状态足以支撑当前单机规模，并能在 PM2 重启后保留额度和提醒。
- 把 policy、执行容量和生命周期拆成职责单一模块，后续调整限额无需继续扩大 `index.js`。

### 拒绝的替代方案

1. **最小内存护栏**：实现最快，但重启会清除额度和队列状态；规则容易继续散落在 `index.js`，不能可靠执行每日预算。
2. **SQLite 持久队列与账本**：恢复和审计能力最好，但当前规模不需要 schema、迁移、worker 和额外运维复杂度。
3. **只依赖 OpenRouter 账户限额**：无法提供每用户公平性、队列保护或良好降级体验，而且本地并发仍可能拖垮机器人。

## Design

### 1. 请求类别与权限边界

Policy Guard 根据发送者、聊天和功能类别返回 `allow`、`degrade` 或 `reject`：

| 类别 | 示例 | 默认策略 |
|---|---|---|
| 低成本公开功能 | `!help`、静态健身计划 | 公开，仅做宽松防刷屏 |
| 外部网络功能 | 天气、新闻抓取、汇率 | 公开，独立网络限流与 timeout |
| AI/高资源功能 | 智能回复、`!ask`、翻译、新闻总结、偏好提取、澄清、建站 | 每用户限流、全局并发、队列和预算控制 |
| 敏感管理功能 | `!groups`、广播、建站、删除网站、自动回复管理 | owner 或明确白名单；额度不能替代授权 |

普通用户只看到“请求太频繁”“AI 繁忙”或“今日 AI 额度已满”等简短信息，不暴露内部预算细节。日志记录具体拒绝原因，但不得记录 API key、完整手机号或用户消息正文。

### 2. 默认额度与自动降级

所有数值均可通过环境变量调整，配置错误时使用安全默认值或在关键配置缺失时启动失败：

- 单用户 AI：每 10 分钟最多 5 次，每天最多 30 次。
- 全局 AI 并发：2。
- 等待队列：最多 20 个请求，最长等待 30 秒。
- OpenRouter 每日硬预算：US$3。
- owner 可绕过个人次数限制，但不能默认绕过全局 US$3 硬预算；紧急时由管理员修改环境配置。

预算阶段：

| 已用预算 | 行为 |
|---|---|
| 0–70% | 正常首选模型链与标准输出上限 |
| 70–90% | 只用最便宜的合格模型，并降低最大输出 token |
| 90–100% | 继续便宜模型；拒绝建站等高 token 功能 |
| 100% | 拒绝所有新 AI 请求；非 AI 功能继续 |

请求发送前根据模型与最大 token 做保守预算预留，完成后按 provider 返回的实际 token/费用结算；缺少实际费用时按配置价格估算。排队超时、取消或调用失败必须释放未使用预留，防止假性耗尽。fallback 只有在剩余预算允许时才能继续。

### 3. 组件边界

#### `protection/policy.js`

- 定义功能类别和敏感权限规则。
- 组合用户身份、限流结果、预算阶段与系统负载。
- 返回结构化决策及内部 reason code。

#### `protection/rate-limiter.js`

- 管理每用户 10 分钟滑动窗口和每日次数。
- 为低成本、网络和 AI 功能提供不同 bucket。
- 使用不可逆摘要或遮罩后的用户标识写日志。

#### `protection/usage-ledger.js`

- 保存当前日期、已结算费用、预留费用和按模型汇总。
- 跨 PM2 重启恢复，按配置时区安全地每日重置。
- 提供原子 `reserve / settle / release` 接口，避免并发超支。

#### `protection/ai-executor.js`

- 成为唯一 OpenRouter 调用入口。
- 实施全局并发、有限公平队列、排队超时、模型降级和 fallback 停止条件。
- 普通聊天、新闻总结、偏好提取、澄清、汇率分析和建站均不得绕过。

#### `lib/atomic-json.js`

- 统一实现“写临时文件 → 关闭/同步 → rename”流程。
- 保留最后一个有效 `.bak`。
- 读取失败时隔离损坏文件并尝试备份；不能把唯一损坏副本静默转换为空对象后覆盖。

#### `lifecycle.js`

- 保存 cron task 句柄并确保只注册一次。
- 管理 WhatsApp 连接状态和重连控制器。
- 采用 5 秒起步、最大 5 分钟、带随机抖动的指数退避。
- 连续离线 15 分钟后主动退出，由 PM2 重新拉起。

#### `reminder-store.js`

- 持久化提醒的 ID、目标、内容、到期时间和发送状态。
- 启动时恢复未来提醒；已过期且未发送的提醒只补发一次，然后清除。

### 4. 数据流

```text
WhatsApp 消息
  → 身份与功能分类
  → Policy Guard
      ├─ reject  → 用户友好提示
      ├─ allow   → 普通功能处理器
      └─ AI/degrade
           → 用户限流
           → Usage Ledger 预算预留
           → AI Executor 有限队列
           → OpenRouter 调用 / 受预算约束的 fallback
           → Usage Ledger 结算或释放
           → 回复用户
```

所有拒绝、排队超时和 provider 失败都必须走统一清理路径，确保并发槽位和预算预留不会泄漏。

### 5. 运行可靠性

1. 启动时验证 OpenRouter key、时区、cron 时间、预算、并发、队列和限流配置。
2. cron task 在生命周期初始化阶段创建一次；后续 `ready` 事件只更新连接状态。
3. 断线持续重连而不是只尝试一次；长期离线触发退出，让 PM2 完整重建进程和浏览器状态。
4. memory、cache、autoreply、session、usage ledger 和 reminders 全部迁移到 `atomic-json`。
5. 新闻 feeds 使用并发 3 的有限并行；单个来源失败不阻塞其他来源。
6. 晨间新闻目标先选择 `GROUP_ID`，不能因为缺少 `MY_NUMBER` 提前返回。
7. 每日向管理员输出简短运行摘要：AI 请求数、拒绝数、估算费用、最高队列深度、重连次数和 cron 成功/失败。

### 6. 错误处理

- **用户超限**：返回冷却提示，不进入队列、不预留预算。
- **队列满或等待超时**：立即释放预留并返回繁忙提示。
- **OpenRouter 失败**：仅在预算允许时尝试便宜 fallback；全部失败后释放剩余额度。
- **状态文件损坏**：隔离、尝试备份、记录高优先级日志；禁止静默清空后覆盖。
- **cron 单项失败**：记录本次失败，不阻止其他任务或下一次调度。
- **配置无效**：安全关键值导致启动失败；可选值回退默认并明确告警。

### 7. 测试策略

- 使用 fake clock 验证 10 分钟窗口、每日次数、日期重置和时区边界。
- 模拟并发预算预留，证明多个请求不能共同突破 US$3。
- 多用户压力测试验证全局并发不超过 2、队列不超过 20，并保持跨用户公平。
- mock OpenRouter 验证 70%、90%、100% 三个降级阶段、fallback 停止与预留释放。
- 模拟重复 `ready/disconnected`，验证 cron 不重复、重连持续退避、15 分钟 watchdog 退出。
- 故障注入测试截断 JSON、rename 失败、备份恢复和损坏文件隔离。
- 使用 fake timer 验证提醒重启恢复、过期补发一次和发送去重。
- 验证新闻有限并行和 group-only 目标。
- 保留现有 XSS 与跨用户缓存隔离安全回归测试。

## Open Questions

当前没有阻塞规划的问题。实施计划可将默认值作为配置基线；若真实流量显示误伤，再通过环境变量调整，无需改变架构。

## Out of Scope

- Redis、SQLite 或其他数据库
- Web 管理后台与实时图表
- 多机部署或分布式队列
- 按用户收费、订阅或支付系统
- 保存完整用户消息用于审计
- 自动修改 OpenRouter 账户级限额
- 本轮直接部署到生产环境
